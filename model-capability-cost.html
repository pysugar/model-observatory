模型选 Sol 的理由：官方定位覆盖复杂编码、computer use 和专业工作，并以低于 Astra 的成本提供接近的能力；官方选型指南仍要求同任务比较。Luna 适合先试受限的轻任务，Astra 保留为能力或时间更重要时的升级候选；这不构成三者在所有代理任务中的胜负结论。

统一升级与协作规则：主控保持 high，子任务按证据换挡

  1. 派发前先分类：固定步骤交脚本；少量文字 / 字段处理走 Luna；有独立目标、需要多步工具执行的工作才创建子 agent。强依赖同一推理链或同一文件写入时，优先由主控顺序完成。
  2. 给子任务完整边界：目标、输入与引用、可写范围、验收条件、预算和停止条件。默认使用精简任务包；只有依赖此前细节才 fork 全历史。返回状态、证据、改动、验证结果和遗留问题。
  3. 按失败原因升级：缺信息先补；Luna 理解不足直接转 Sol medium；medium 方向正确但复杂度超出时转 high。补证据并纠偏一次仍重复同错，交回主控或独立专家，不继续同档空转。连接、认证、限流或 schema 错误先修调用条件。
  4. 把 xhigh 留给具体难点：Sol / Opus / Astra high 的因果链或约束推演仍不足时，单开专家子任务试 xhigh；max 仅在该类任务已观察到增益时使用。主控的模型和 high 档位保持固定。
  5. 先小规模并行：建议从同时 2 个子 agent、1 层委派起步，属于成本与协作上的策略假设。并行只拆独立工作；代码写入按文件归属或隔离 worktree，整合与最终验收由主控完成。
  6. 按成功任务算账：合计主控、所有子 agent、辅助调用、工具、重试与缓存写入费用；另记人工返工和端到端耗时。预算 / 迭代耗尽记为 partial 或失败，不算已完成；回退模型的身份和档位也记录下来。

升档还是换模型：四条速记

  1. 先补信息：缺日志、复现、原始材料或工具结果时先补齐；信息齐全但推理不足才升档。
  2. 常用升级是 medium → high：high → xhigh 应针对具体遗漏；只有已见额外收益、任务价值高且输出预算足够时才试 max。
  3. 重复同一种错误就换视角：补充证据后仍走同一路径，可让另一模型依据复现、约束与失败记录独立分析。
  4. 验收后再固定配置：看完成率、等待时间与人工返工，不用同名档位或单价代替任务结果。

按阶段调档：方案设计 high → 明确实现 medium / high → 重要审查 high → 执行回归 low；未知失败再回到 high 定位。

如何理解“1M 上下文”和多模态支持
上下文上限代表可容纳量，不保证长文档推理或信息召回质量。Argon 的 1,048,576 是输入、思考、输出共享窗口；Flash / Flash-Lite 列的是输入上限，输出另有 65,536 上限。GPT 的窗口为 1,050,000；Claude 4.6 及以后为 1M / 128k；本次核验的 Opus 4.5、Sonnet 4.5、Haiku 4.5 为 200k / 64k。旧评测页面的窗口标注不覆盖当前官方规格。
表中只列这些通用 API 模型的原生输入和文本输出。GPT / Claude 的产品或工具可以处理其他媒体，但不应据此把通用模型标为原生音频、视频输入；Gemini 的音频/视频理解也不等于能生成音频/视频。图像生成、TTS、Live 与视频生成另有专用模型。

这是费用情景，不是实测成本。每次请求的 token 数相同，不能保证不同模型完成同一任务会使用同样的 token。

  

    
    
    
    
    
    
  
费用＝[输入×(1−缓存占比)×输入价＋输入×缓存占比×缓存读取价＋(可见输出＋推理)×输出价]÷1,000,000×请求数。缓存比例表示已有命中，不包含建立缓存的写入/存储成本。工具、检索、区域加价、税费、失败重试与人工复核另计。超出窗口或同步输出上限时不估价。

一个足够简单的选型流程
  1. 先固定真实任务、输入材料、工具权限、输出预算与验收标准。
  2. 选 2–3 个模型，先测默认或中档；预算允许的高难度任务，可加入高档作为能力上限候选。
  3. 若质量不达标，比较升档与换模型；若质量相同，再看费用和完成时间。
  4. 分开记录正确性、交付完整性、格式、人工返工；保留所有失败和超时，不能只算成功样本。
  5. 用同题配对、随机顺序与多次重复确认小差异；中文内容用匿名人工评价补充英文榜单。
